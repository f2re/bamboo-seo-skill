# Данные и обратная связь

Настройки находятся в `bamboo.json.analytics`. Секреты — только переменные окружения;
программа не читает `.env` автоматически. В PowerShell задавайте `$env:NAME="значение"`,
в shell — `export NAME="значение"`. Не вставляйте секреты в задания модели, Git или логи.

## Google Search Console

`gsc_property`: точное подтверждённое свойство, например `sc-domain:example.org` или URL-prefix.
В Google Cloud включить Search Console API, настроить OAuth-клиент и согласие владельца,
дать scope `https://www.googleapis.com/auth/webmasters.readonly`.
Получение первого согласия/refresh-token выполняется штатным OAuth-процессом, не внутри скилла.

Поддерживается готовый `BAMBOO_GSC_ACCESS_TOKEN`, либо набор
`BAMBOO_GSC_CLIENT_ID`, `BAMBOO_GSC_CLIENT_SECRET`, `BAMBOO_GSC_REFRESH_TOKEN`.
Во втором случае CLI обновляет access-token запросом к официальному token endpoint.
Истёкший access-token, если он задан, не подменяется молча другим аккаунтом: уберите его
для использования refresh-набора. Авторизованный аккаунт должен иметь доступ к свойству.

Выгружаются два независимых слоя:

- `grain=page`: `date,page`;
- `grain=page_query`: `date,page,query`.

Они **не складываются**. Второй слой используется для реальных query×page-insights и кандидатов
на несколько URL по одному запросу. Такой кандидат ещё не доказывает SEO-каннибализацию:
нужно проверить назначение страниц и фактическую выдачу.

API имеет ограничения полноты и приватности. Дни GSC определены в Pacific Time. Обычно выбирать
завершённый период с запасом на задержку, а не требовать итоговые показатели за текущий день.

## Яндекс.Вебмастер

`yandex_user_id` и `yandex_host_id` взять из официального API под своей OAuth-авторизацией,
после подтверждения прав на сайт. `BAMBOO_YANDEX_TOKEN` — токен приложения с доступом к Вебмастеру.

Обычный сбор использует `v4/query-analytics/list` дважды:

- `text_indicator=URL` → `grain=page`;
- `text_indicator=QUERY` → `grain=query`.

Доступны последние две недели. Для `grain=query` API возвращает
`popular_complementary_indicator=URL`. В Bamboo этот URL сохраняется в поле `page` как
**подсказка page_hint** для отчёта. Это самый популярный связанный URL, а не полный разрез
query×page и не доказательство атрибуции всех показов/кликов этому URL.

Яндекс также предоставляет отдельную β-выгрузку настоящих данных URL×query с датой, регионом,
кликами, показами и позицией; архив доступен существенно глубже обычного Query Analytics.
Эта выгрузка асинхронная, расходует квоту и может формироваться долго, поэтому weekly-сбор
намеренно не запускает её автоматически. Контракты перечислены в `docs/SOURCES.md`.

Частый обычный сбор накапливает собственную историю в SQLite. Отсутствующий показатель
сохраняется NULL, а не нулём. В `pull-yandex.json` фиксируются границы и ограничения выгрузки.

## Унифицированный CSV

Обязательные заголовки: `date,source,grain,page,query`.
Метрики: `impressions,clicks,position,product_clicks,leads,orders,revenue,cost`.
Пустая ячейка означает «не измерено». Нулевое значение — измеренный ноль.

Поддерживаемые grain:

- `page` — итог страницы;
- `page_query` — точный разрез страница×запрос, например GSC;
- `query` — агрегат по запросу без полной страничной атрибуции, например обычный Яндекс Query Analytics;
- `conversion` — собственная атрибуция переходов к товару/обращений/заказов.

Для `query` поле `page` может быть пустым либо содержать provider-specific hint; Bamboo не
складывает такой ряд со статистикой страницы. Для `conversion` источник должен отражать реальную
схему атрибуции. Нельзя присваивать один заказ нескольким источникам как независимые продажи.

Финансовые значения в одной выгрузке должны быть в одной заранее согласованной валюте;
конвертация валют и бухгалтерский расчёт прибыли не выполняются. Удалите имена, телефоны,
email и тексты переписки покупателей. В URL/запросах тоже не должно быть персональных данных.

Ключ SQLite — `(date,source,grain,page,query)`. Повторный импорт делает upsert.
Дубликаты ключа внутри одной выгрузки, NaN, отрицательные метрики и неверные даты отвергаются
до записи всего набора. Источник не обязан иметь строку за каждый день: отсутствие строки
не считается измеренным нулём.

## Отчёт и решения

`analytics-report` теперь имеет четыре независимых блока:

1. `pages` — итоговые URL;
2. `queries` — Google page_query и Яндекс query;
3. `cannibalization_candidates` — только там, где реально известны несколько URL для одного
   query, сейчас это прежде всего GSC;
4. `conversions` — product_clicks, leads, orders, revenue и cost отдельно от поисковых метрик.

Для запросов добавляется `intent_hint`: branded / transactional / commercial_research /
informational / unknown. Это **лексическая эвристика для triage**, не SERP-анализ и не основание
автоматически менять страницу.

CTR рассматривается вместе с позицией и составом запросов. Низкий CTR сам по себе не является
ошибкой. Рост кликов выводится только при сопоставимом покрытии периода. Страница с малой выборкой
не удаляется. Один запрос у двух URL — сигнал проверить архитектуру, а не команда удалить слабый URL.

`bamboo-analyst` предлагает максимум три проверяемые гипотезы с метрикой и условием отката.
Изменение `content/strategy.md`, текста или публикации требует решения владельца.

## Регулярный запуск

Планировщик не устанавливается и ничего не активируется при установке.
Один проход:

```bash
python tools/weekly.py --workspace /путь --provider google --end YYYY-MM-DD
python tools/weekly.py --workspace /путь --provider yandex --end YYYY-MM-DD
```

Скрипт берёт 14 дней, затем строит два семидневных периода, не вызывает модель и не публикует.
В установленном проекте его путь `.bamboo/toolkit/tools/weekly.py`.
Для Яндекса не откладывайте обычный Query Analytics за пределы двухнедельного окна.
Для Google параметр end без явной даты использует UTC-дата минус четыре дня как консервативную
эвристику задержки; для Яндекса — вчера по UTC.
