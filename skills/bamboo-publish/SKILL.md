# bamboo-publish

Это сценарий с внешними последствиями. Выполнять только по явному поручению пользователя
на конкретный материал и канал. Прочитайте docs/SECURITY.md и публикацию в README.md.

Сначала validate и status. Нужны актуальный approval и неизменённая человеческая рецензия.
Не подделывать рецензию, не изменять хеш ради прохождения контроля, не отправлять материал
в обход CLI. При недостающем разрешении остановиться с конкретным объяснением.

export создаёт локальное превью. publish без --execute — только план без сети.
WordPress --execute по умолчанию создаёт/обновляет draft. --live требует текущий полный
--confirm и явное разрешение на публичный выпуск. Не считать разрешение создать черновик
разрешением сделать публикацию. Публичную запись нельзя случайно вернуть в draft: CLI откажет.
Обновление публичного материала также требует --live и разрешения владельца.

При pending выполнить wp-reconcile (чтение) и разобрать результат; не удалять ledger
и не повторять POST вслепую. Не переназначать ID чужой записи. static --execute только
собирает site локально; ВКонтакте получает ручной экспорт. Не говорить «опубликовано», если
не было фактической отправки или ответа сервера. Секреты не показывать в выводе.

Выход: канал, фактическое состояние, ID/URL ответа сервера либо путь локального пакета.
После публикации проверить результат в доступном браузере; если браузера нет, указать
непроверенные визуальные аспекты. Дата/авторство/источники не должны исчезать в шаблоне CMS.
